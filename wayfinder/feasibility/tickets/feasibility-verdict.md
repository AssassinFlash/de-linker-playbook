# 可行性裁定

## Question

综合前六票：本仓库在现有基础上补齐到闭环是否可行（缺口均有已验证路径可补），还是需要从零开始？给出结论、理由与补齐顺序（Google 渠道先通）。与用户对谈定稿（HITL）。

须一并裁的点（由前序票带出）：
- 编排从瀑布改为「读反馈选下一步」的循环、两线拆台账——算补齐还是局部重写，范围多大（「现仓库闭环缺口审计」#3 #4）。
- 补齐顺序里 GA4 + 同意横幅与「先只上 GSC」的先后（「Google 渠道接入路径」）。
- playbook → 新站的交接面由谁、以什么形式承接（审计 #6；用户不亲自部署）。
- 获客线按陌生开发，名单作为种子输入怎么接进现流水线（审计 #7，已降为中）。
- 操作者无行业判断依据时，验证层靠什么（审计 #8，Notes「操作者是新入行者」）。

## Resolution

2026-10-14 与用户对谈定稿（两轮拷问，Q1–Q10 全部同意，Q5 重讲后同意）。术语见 `CONTEXT.md`。

**结论：补齐，不从零开始；编排与台账局部重写。**

- 从零开始换不到更好的底座：开源参照无 A 档闭环（「开源参照全景」），「反馈回流 → 决定下一步」这段在任何底座上都得自接。
- 方法层留用：源自 coreyhaines31/marketingskills，审计无致命缺口；事实底座换为三方映射（竞品调研 + 线上站点 + 新站仓库）。
- 致命缺口集中且有界：2 个编排 skill、台账结构、新建取数脚本层；另有 101 处写死路径的机械替换（「现仓库闭环缺口审计」）。
- 每个缺口都有已验证路径：GSC / Sheets 走服务账号 + 官方客户端；L3 读 Woo；回复走 IMAP（imap_tools 等）；看板用 Looker Studio 原生连接器。

**定下的形态**

| # | 决定 |
|---|---|
| Q2 | 保留阶段作为**冷启动阶段**；走完不 stop，转入**运营循环**：每次「下一步」先读反馈，按反馈分级规则挑下一个动作。 |
| Q3 | 台账拆两张（营销、获客各管自己的阶段与下一步）；执行登记与反馈数据两线共用一张**底表**。 |

**补齐顺序**

0. 换事实源（101 处写死 New → 三方映射）+ 台账拆两线。前置：不做则任何一次运行都读过期事实、两线互相覆盖。
1. Google 渠道：GSC 网址前缀资源 + 验证（站点接入，agent 做）→ Cloud 项目与服务账号 → 底表（执行登记 + 反馈）→ 取数脚本回流 L1/L2 → Looker Studio 看板。
2. L3：读 Woo 询盘写入底表。
3. 编排改循环：冷启动阶段走完转运营循环，「下一步」读反馈选动作；证据闸 + 反馈闸替换用户审批。
4. 邮箱 IMAP 只读回流（获客线 L2 回复）。
5. GA4 + 同意横幅（站点接入，agent 做）。
6. 激活名单入口（获客第 2/3 阶段以名单为起点）。
