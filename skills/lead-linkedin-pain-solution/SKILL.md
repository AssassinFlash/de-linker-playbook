# LinkedIn 痛点-方案帖（Structure 5）

根据已批准 ICP 与可核验的运营痛点，写一篇 Problem/Solution/Benefit 帖，落到 `deliverables/lead/08-linkedin/`。本 skill 只产帖稿；缺证据标缺口，不编造。

## 步骤

1. **共用规则**。读 `skills/marketing-playbook-standards/SKILL.md`。完成：能复述数据锚定、例子禁引用、产出根、工具写能力。

2. **输入**。产品与公司事实读事实源入口 `docs/fact-sources.md`，按其「什么问题查哪个源」取证；查不到标〔未证实〕，按没有处理。硬依赖：已批准的 `deliverables/lead/01-icp/icp-analysis.md`。软依赖（有则读，不阻塞）：`deliverables/lead/05-usp/usp-strategy.md`、`deliverables/lead/05-usp/product-knowledge.md`、`deliverables/lead/08-linkedin/topic-research.md`。用户本轮给出的受众、痛点、产品能力或 CTA 视为本轮输入，来源记「用户本轮」。受众、品类或「产品能解哪类运营痛」仍缺到无法下笔时，打开 `skills/lead-interview/SKILL.md`（存在则按其做）；不存在则把缺口写入台账，不在本文件另写问卷。完成：能指出受众、角色、已知痛点、2–3 条相关能力各依据哪几条；原文不拷进本仓库。硬依赖缺失、用户本轮也未给出对应全文、且无 `user_waiver` → 停。

3. **确认画像**。从 ICP 抽出本帖受众：行业、典型角色、目标、现状、正在用的替代方案。多画像时，用户本轮点名则用该画像；未点名则用 ICP 中的优先画像，并在交付物标明。完成：一段可检查的画像摘要，每项能指回 ICP 或用户本轮。

4. **识别并选定痛点**。读 `references/pain-categories.md`。对照画像挑战与产品能力，只列入产品**确实能解**的运营痛点，按五类归档。痛点必须是买家视角、具体、能接到一条产品能力。区域气候或当地法规障碍 → 停，宣布应走 `skills/lead-linkedin-market-challenge/SKILL.md`（文件不存在则只报缺口），本文件不写。采购关系恐惧（沟通、付款、批次一致性承诺）→ 停，宣布应走 `skills/lead-linkedin-buyer-concern/SKILL.md`。错误信念 → 停，宣布应走 `skills/lead-linkedin-mythbust/SKILL.md`。用网页搜索核验「该受众是否真有此痛」以及未解决的后果；需要原文则抓取指定 URL。查询意图见 `references/pain-categories.md`。ICP 已写明该痛且本帖不用数字时，搜索日志写「本轮未检索；痛点取自 ICP」。搜索不可用：无 ICP 痛点则停并写缺口；有 ICP 痛点则继续，但禁止写成本或影响数字。禁止为凑次数空搜。禁止编造停机成本、返工率、ROI。选定：用户本轮点名且属运营痛 → 用该条（仍须买家视角 + 能被能力接住 + 非分流）。未点名：本轮能问则只问选哪条，先不写帖。用户已说直接做、或本轮不能问 → 取证据最强的一条，交付物标明「痛点未经用户确认」。一条都核验不了 → 停，只交分类清单，不写帖。完成：分类表每条有类别、买家视角表述、证据（ICP 段落或 URL）、所接产品能力；点名或不能问时选定恰好一条；能问且未点名时只问了选哪条、未写帖。

5. **起草**。读 `references/structure-5.md` 与 `skills/lead-generation/references/linkedin-post-guidelines.md`。按 Structure 5 写一篇英文帖：Hook → Elaboration → Solution → Benefits → CTA。一帖只解选定的那一条痛。利益句把能力接到该痛的结果，不堆规格。CTA：用户本轮指定则用（须落在共用规范的四种之一）；否则用接到该痛的评论型问句。标签、篇幅、钩子位置、软广只按共用规范，不在本文件重写。用户点名微博客 / 故事叙事 / 滑梯式 / 直销节奏时，按共用规范只改语气与结构，不改核心信息。面客语种缺省英语；策略笔记用本轮语言（缺省中文）。多画像需隔离时 dispatch a subagent, else do it inline。完成：一篇可复制英文正文；五段齐全；含数字的句子能指回来源。

6. **质检并落盘**。对照本文件清单与共用规范出门清单。写入 `deliverables/lead/08-linkedin/pain-solution-post.md`。不代发布：`publish_status: copy_only`。过证据闸、审稿到 `operator_ok` 后由操作者亲手发，发完走执行登记（`skills/marketing-execution-log/SKILL.md`）。完成：主文件非空；分类痛点、选定痛、特征-利益映射、英文正文、中文策略说明均在；教学例子原文零出现。验证—审查—审批走 `skills/lead-generation/references/orchestration-protocol.md`，本 skill 不代替审批、不代替发布。

## 默认

- 产品与公司事实读事实源入口 `docs/fact-sources.md`，按其「什么问题查哪个源」取证；查不到标〔未证实〕，按没有处理；不在本仓库另存档案。
- 硬依赖是已批准 ICP；软依赖是 USP、产品知识、话题研究。闸门口径见 `skills/lead-generation/references/dependency-graph.md`。
- 查证用网页搜索；需要原文时抓取指定 URL。搜索不可用则停止数字并写缺口，不编造。不并列搜索引擎菜单。
- 本 skill 只产帖稿，不发布，也不经任何工具代发布；发帖一律由操作者亲手做。
- 数字、证书、案例、产能、交期、价格：产品上下文或已抓取页里有才写。没有就写「未在上下文出现」或删掉该句。
- 进度只认台账。产出只进 `deliverables/lead/08-linkedin/`。
- 分析与缺口用本轮语言（缺省中文）；帖子正文与标签缺省英语。同一段不中英混排。
- 选题卡走 `skills/lead-linkedin-topic-research/SKILL.md`（文件存在时）。多平台日历或战役走 `skills/marketing-social-content/SKILL.md`（文件存在时）。本文件不写区域挑战帖、关切帖或揭谣帖。

## 写法

- 功能不是痛点。先写买家正在付的代价，再出现产品。
- 一帖一条痛。多条痛就多篇，不塞进同一帖。
- Structure 5 五段顺序固定，细则见 `references/structure-5.md`。
- 利益必须能回溯到选定痛：每条利益回答「所以这条痛怎么减轻」。列不出「所以呢」的规格句删掉。
- 方案段是自然答案，不是规格表。软广上限按共用规范：去掉产品句后，痛与影响仍应对该买家有用。
- 未解决后果只写有来源的数字，或只写 ICP 里的定性后果。禁止用「每小时 $X」这类无来源金额。
- 不承诺点赞、评论或互动率。

## 例子

> 仅供理解，禁止引用到输出。

输入写「净价可见、交期可锁、售后代跑」。这是能力不是痛点。对照批发–安装商摩擦表那种「摩擦 | 买家实际损失 | 出现位置 | 证据」多行结构，成稿应改成该 ICP 已批准的**一条**运营损失画面（锁价看不到净价、当场无法给自家客户报价；送货日不绑定、班组已排脚手架已立），而不是把整张摩擦表或同档批发店共用的 FAQ 题型写成帖。点结构特征可以（同档店登录后才见净价、送货日写明不绑定），不要照抄店名原句或条款号。RMA 推回厂家、到货即验属于采购关系恐惧，分流关切帖，不硬写成运营痛。没有停机成本数字就写「未在上下文出现」，不编每小时损失；班组空等、项目顺延、电话催单只作定性后果。方案段只解选定那一行的损失，用该行「买家实际损失」核对「所以呢」，不承诺库存数量或默认绑死交期，也不把制造商/备件库写进身份。利益句必须接到这条痛，不堆规格。不要把本节句子粘进交付物。

## 易错

- 没读已批准 ICP 就发明痛点。
- 把功能、产地或规格写成痛点。
- 一帖塞多条痛，或把区域法规、采购关系恐惧、行业误区写成「运营痛」。
- 编造停机成本、返工率、ROI 或客户引言。
- 方案段堆型号，利益句接不回选定痛。
- 把教学例子或共用规范原文写入交付物。
- AI 代发或代发布（不论是否配置工具、用户是否要求），或把成稿当成已发出。
- 预测点赞或互动率。
- 终稿残留未解释的 `{{...}}`。
