# LinkedIn FAQ 帖（Structure 14）

把买家真正会问的一条事实问题写成可发布的 LinkedIn FAQ 片段帖：公开答案有用，项目细节走私信。落到 `deliverables/lead/08-linkedin/`。本 skill 只产帖稿；用户自行发布，或经用户已配置的工具发布。MOQ、交期、样品、付款等政策缺证据则标缺口，不编造。

## 步骤

1. **共用规则**。读 `skills/marketing-playbook-standards/SKILL.md`。篇幅、钩子、CTA、标签、四种风格、软广：读 `skills/lead-generation/references/linkedin-post-guidelines.md`（只遵守，不把该文抄进本文件或交付物）。完成：能复述数据锚定、例子禁引用、产出根、工具写能力，以及本帖必须走 Structure 14。

2. **输入**。产品与公司事实读事实源入口 `docs/fact-sources.md`，按其「什么问题查哪个源」取证；查不到标〔未证实〕，按没有处理。硬依赖：已批准的 `deliverables/lead/01-icp/icp-analysis.md`。软依赖存在则读：`deliverables/lead/05-usp/usp-strategy.md`、产品知识稿（`deliverables/lead/05-usp/product-knowledge.md` 或 `deliverables/lead/10-sales/product-knowledge.md`，以磁盘已有为准）、`deliverables/lead/08-linkedin/topic-research.md`。用户本轮给出的品类、受众、已知提问领域、指定 FAQ、公开答案、CTA 一并吸收，来源记「用户本轮」。原文不拷进本仓库。硬依赖文件缺失、本轮也未给出受众与至少一条事实问题、且无 `user_waiver` → 停。ICP 文件缺失但本轮已给受众与问题：继续，交付物注明「ICP 未在上游出现」。品类或受众仍不清：打开 `skills/lead-interview/SKILL.md`（存在则按其做），否则停并只要这两项。不要在本文件另写问卷。完成：能指出品类、受众、将答的问题各依据哪几条。

3. **发现 FAQ**。用户本轮已给出确切问句 → 记入候选表并跳到步骤 4。否则读 `references/faq-discovery.md`，从 ICP、本轮已知领域、话题研究抽出 2–3 条买家属问句，每条附一句建议答案或 `[待补充]`。建议答案只能来自产品上下文、本轮或已查证页。需要确认「有人真问」、或答案涉及标准 / 认证 / 流程时，用网页搜索查证；需要原文则抓取指定 URL。搜索不可用：只用 ICP / 本轮已有问题，不编造新 FAQ。禁止为凑次数空搜。本轮能问则只问一句选哪条；用户已说直接做、或本轮不能问 → 取证据最足的一条，交付物写「FAQ 未经用户确认」。完成：候选表 2–3 行（或本轮指定 1 行）；入选是问句；与关切 / 揭谣 / 教育帖不混。

4. **锁定答案与 CTA**。读 `references/structure-14.md`。成稿最低两项：一条买家属问句 + 一条可公开的简短答案。缺答案：不编造政策数字。公开答案必须具体、对匿名读者有用，同时留出项目细节走私信的空间；禁止把「视情况而定」当成唯一句。禁止写出未公开报价或成本结构。CTA 用户点名则用；未点名按 guidelines 在评论型 / 连接型 / 私信型 / 混合里选一个接到「要项目细节」。完成：问句、公开答案、CTA 类型、是否含产品句（最多 1–2 句）已写入映射。

5. **起草**。按「写法」写一篇完整可复制的英文帖，严格 Structure 14 五拍：Hook → FAQ → Answer → Offer for more detail → CTA。用户点名微博客 / 故事叙事 / 滑梯式 / 直销节奏时，按 guidelines 只改语气与结构，不改问句与答案事实。面客语种以产品上下文为准（缺省英语）；策略笔记用中文；同一段不中英混排。完成：五拍齐全；钩子落在折叠前；去掉产品句后帖子仍有用；恰好一个 CTA；文后 3–5 个标签。

6. **质检并落盘**。按清单与 guidelines 出门清单自检后写入 `deliverables/lead/08-linkedin/faq-post.md`。不代发布：`publish_status: copy_only`。过证据闸、审稿到 `operator_ok` 后由操作者亲手发，发完走执行登记（`skills/marketing-execution-log/SKILL.md`）。完成：主文件非空；含候选 FAQ、入选理由、英文帖、中文策略、来源、搜索日志、缺口；教学例子原文零出现。验证—审查—审批走 `skills/lead-generation/references/orchestration-protocol.md`，本 skill 不代替审批、不代替发布。

## 默认

- 产品与公司事实读事实源入口 `docs/fact-sources.md`，按其「什么问题查哪个源」取证；查不到标〔未证实〕，按没有处理；不在本仓库另存档案。
- 硬依赖：已批准 ICP。软依赖：USP、产品知识、话题研究。产地、供应地、目标市场以产品上下文为准，不预设某一出口国。
- 本帖类型只答 **事实问题**（MOQ、交期、样品、付款、包装、质检流程、定制边界）。情绪顾虑走 `skills/lead-linkedin-buyer-concern/SKILL.md`（文件存在时）。揭穿误区走 `skills/lead-linkedin-mythbust/SKILL.md`（文件存在时）。教选购或操作走 `skills/lead-linkedin-education/SKILL.md`（文件存在时）。选题卡走 `skills/lead-linkedin-topic-research/SKILL.md`（文件存在时）。多平台日历或战役走 `skills/marketing-social-content/SKILL.md`（文件存在时）。本文件不写那些帖型。
- 查证用网页搜索；需要原文时抓取指定 URL。不并列搜索引擎菜单。搜索不可用则停止编造新 FAQ 与未核验标准，并写缺口。
- 发布：AI 不代发布（不论是否配置工具、用户是否要求），只产帖稿；发帖一律由操作者亲手做。
- 进度只认台账。产出只进 `deliverables/lead/08-linkedin/`。Markdown only，无 Excel。
- 单帖 inline 做完。需要隔离时 dispatch a subagent, else do it inline。
- 数字、证书、MOQ、交期、付款条件、样品规则：产品上下文、用户本轮或已抓取页里有才写。没有就写「未在上下文出现」或 `[待补充]`，禁止补造。

## 写法

- **Structure 14（固定五拍，顺序不改）**；展开规则见 `references/structure-14.md`。
  1. Hook：表明在回答该受众的常见事实问题（有来源的数字、反直觉判断、ICP 痛点提问、场景或拆穿误区，择一；开场规则见 guidelines）
  2. FAQ：买家属问句，单独成行或加粗
  3. Answer：短、直接、可核验；有数字则有来源
  4. Offer for more detail：公开答案仍成立，邀请按项目补细节
  5. CTA：用户指定的那一个；未指定则接到「要项目细节 / 样品条件 / 包装规范」
- 一帖一问。多问拆成系列，不塞进同一帖。
- 答案给真实公开信息，不是把关键句藏起来再逼私信。私信提供的是规格、MOQ 档位、交期按单计算，不是把公开答案掏空。
- 软广：产品最多 1–2 句且可删；删掉后帖子仍应能答完这个问题。规格堆砌删掉。
- 短段、段间空一行。非专家买家读得懂；必要术语跟一句人话。
- 标签 3–5 个，放 CTA 之后；组合见 guidelines。品类标签取产品上下文，不在本文件填值。话题标签可绑该 FAQ 主题。

## 例子

> 仅供理解，禁止引用到输出。

输入写「常有人问起订量」。先定桶：同档批发店 FAQ 共用的交易问——订货/付款、发货/到货、到货损伤与退货、保修找谁办——不是厂家页上的故障码/症状诊断，也不是登录墙或「你们装不装机」。一帖只取交易桶里的一句，问句用干活的人口吻（最低订量、账期、到货日绑不绑得住），不要写成卖方栏目名。

草稿的公开答案只用上下文里已有的政策或流程，短、当场能用（店级 FAQ 的答句密度），问的是订量就答订量，不要改口成排查脚本或「去问厂家」。没有数字就标缺口，不写「看情况 / 行业领先交期」，也不把别人店里的时限、免运门槛、退货费率或整张店级问答表塞进同一帖，更不要写成只有标题、答案藏在工单后的厂家路由页。钩子点明这是常见事实问题，结尾一个 CTA 请对方带项目细节来。不要把本节句子粘进交付物。

## 易错

- 没读 ICP 与产品上下文就发明「买家常问」或编造 MOQ / 交期 / 付款。
- 把教学例子或搜到的 FAQ 帖原文写入交付物。
- 把关切、揭谣、选购技巧写成 FAQ。
- 一帖塞多个问题，或答案空到只剩「视情况而定」。
- 把未公开报价写进帖子，或把公开答案掏空只为逼私信。
- 无来源的统计、认证、互动率承诺。
- AI 代发或代发布（不论是否配置工具、用户是否要求），或把成稿当成已发出。
- 终稿残留未解释的 `{{...}}`，或把 `[待补充]` 假装成已核实政策。
